# 画像編集のメモリ管理 — 1.8.3

更新: 2026-09-13 / versionCode 93

「次の作業を進める」指示を受け、[実装設計](IMAGE-EDITOR-ROADMAP.md) の CE0-B を実装した。本体 MIT を維持し、新規依存は追加していない。[1.8.2 の保存基盤・アイコン](IMAGE-EDITING-1.8.2.md) に続く変更。

## 利用者に届く変更

- 保存・保存容量の計測を始める前に、出力画像と作業領域がメモリ予算に収まるかを確認する。
- 収まらない場合は保存先へ書き込まず、保存時に縮小候補の幅・高さを表示する。「このサイズに変更」を押した場合だけ出力寸法を変える。編集内容は保持し、保存は再度選ぶ。
- 縮小しても処理できる余地がなければ、その旨を知らせて編集に戻る。保存容量の自動計測ではダイアログを繰り返し出さず、計測を停止したことを表示する。
- 表示用プレビューは長辺最大 2048px から、利用可能なメモリに合わせて縮小する。保存の指定寸法とは別に扱う。
- 複数の画像編集画面を開いても、プレビュー・人物/物の自動選択・容量計測・保存準備をアプリ全体で一つずつ実行する。
- 極端な縦長画像でも、出力長辺を指定したときに縮小率 1% の旧制限に引っかからない。

従来の出力長辺上限 8192px は維持する。読み込み時の上限適用は従来どおり。今回のメモリ判定で、それより小さい保存寸法を無断で適用することはない。

## 予算の計算と所有権

`RenderBudget` は Android に依存しない計算として分離した。最終出力だけでなく、間引きデコード、EXIF の向きの変換、縮小中間画像、描画レイヤー、クリップマスク、圧縮・推論の作業領域を概算する。

| 対象 | 今回の扱い |
|---|---|
| 元画像 | `inSampleSize` の境界を含む実際の間引き寸法から算定。切り抜いた場合も、元画像全体のデコードが必要な現行処理を計上 |
| 描画と圧縮 | 出力 1 枚に、段階ごとの最大作業量と固定余裕を加算。計算は Long、極端な寸法では飽和させ、オーバーフローで小さく判定しない |
| 表示中のプレビュー | 全編集画面の参照を弱参照で追跡。旧フレームが保持する画像も GC まで計上し、GPU コピー分の余地を取る |
| 元画像の貸出 | `withBitmap` が描画完了・失敗・取消の `finally` で解放。別のレイヤーや次の処理まで原寸画像を保持しない |
| 表示に渡す画像 | Compose が使用しうる画像を手動で recycle しない。表示へ渡す直前に取消された画像は所有者が解放 |
| 重い処理の実行枠 | `ImageWorkGate` の全画面共通 Mutex。画像の解放と推論器の close まで枠を保持し、待機中の取消では割り当てを始めない |
| 保存容量の計測 | `CountingOutputStream` へ符号化し、圧縮データを捨ててバイト数のみ加算。ByteArrayOutputStream を廃止。品質探索でも同じ方式 |

Android 8 以降では Bitmap の画素は native heap に配置されるため、Java の空きヒープだけでは判断しない。[Bitmap のメモリ管理](https://developer.android.com/topic/performance/graphics/manage-memory)
デコード前の寸法確認と、用途に合わせた間引きを行う。[大きい Bitmap の読み込み](https://developer.android.com/topic/performance/graphics/load-bitmap)

実行枠の取得後に `ActivityManager.memoryClass`、managed heap の空き、native heap の使用量、システムの空きと low-memory threshold を読み直す。[MemoryInfo](https://developer.android.com/reference/android/app/ActivityManager.MemoryInfo)、[native heap の使用量](https://developer.android.com/reference/android/os/Debug#getNativeHeapAllocatedSize())

今回の係数は**実機で校正する前の保守的な初期値**。編集用予算は memoryClass の 75% と最大 384MiB（low-RAM 端末は 96MiB）の小さい方を起点に、表示中画像を控除し、他の空き量でも制約する。managed heap に 24MiB の余地を残す。推論はテンソル・モデル・arena・輪郭処理用に 128MiB を概算に含める。

不足時の候補は、長辺を二分探索して間引き境界ごと再計算する。保存寸法は候補に同意した後だけ変更する。プレビューは長辺 256px、自動選択用の描画は 512px を最低候補とし、元からそれより小さい画像は元寸法を使う。予算不足を極端に粗い推論画像で取り繕わない。

## 検証

- 画像編集 JVM テスト **144 件成功、失敗 0、エラー 0、スキップ 0**（既存 122 件＋追加 22 件）。
- 12MP・48MP・8192 四方、JPEG/PNG/WebP、切り抜き、極端な縦長、整数上限寸法の**予算計算**を検証。提示寸法が同じ予算内に収まり、原本の寸法やレイヤーが変更されないことを確認。
- 別の編集画面のプレビュー、native heap、managed heap、システムのメモリ不足が予算に反映されることを確認。
- 二つの呼出元の排他、待機中の取消、実行中の取消と後片付け、失敗後の再利用を検証。
- 小さなバッファを再利用して 2GiB を計測し、圧縮データを保持せず Int の表示上限を超えても負数へ折り返さないことを確認。
- `:app:assembleDebug` 成功。バージョンを先に 1.8.3 / code 93 へ上げた状態で検証。APK の `com.zerotoship.foldex.debug` / `1.8.3-debug` / code 93 を aapt2 で確認。

## 実機確認と後続作業

今回のテストは Android の Bitmap・圧縮器・推論器を動かす実機測定ではない。予算はピーク使用量を厳密に保証するものではなく、端末・画像形式・GPU・推論ランタイムによって係数の調整が必要。低メモリ端末では自動選択を開始できない場合がある。

実機で確認する項目:

1. 12MP・48MP・8192 四方・極端な縦長・大きい透過 PNG を使い、案内寸法での描画・保存、画素と EXIF、処理時間とピーク使用量を測る。
2. 二つの編集画面で、自動選択・容量計測・保存・取消を続け、終了後に原寸画像が残らないこと、表示に recycle 済み画像が渡らないことを確認する。
3. 縮小候補の適用・取消、出力設定の Undo、画面回転、背景からの復帰、日本語・英語・大きい文字での案内を確認する。

元画像を毎回解放するため、連続プレビューでは再デコードの時間が増える。速度とメモリの実測を行い、必要なら予算付きの縮小キャッシュを後続で検討する。
8192 超の原寸保存・タイル合成と逐次エンコードは CE5。下書きの永続化は CE0-D のままであり、今回保持する編集内容は開いているセッション内のもの。プロセス終了からの復元はまだ提供しない。
次の実装単位は CE0-C（透過・JPEG 背景・撮影情報・目標容量の出力契約）。商用出荷と CE0 全体の完了は未判定。
